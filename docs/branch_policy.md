# Политика веток проекта gazo_analizator

**Дата актуальной сверки:** 02.11.2026.  
**Единственная рабочая ветка:** analysis/vendor-behavioral-reconciliation.  
**Default branch на момент сверки:** main. Переключение на рабочую ветку согласовано пользователем, но должно быть выполнено через настройки GitHub, так как доступный GitHub-инструментарий этой сессии не предоставляет операцию изменения repository settings.

## Правило работы

Все новые изменения, проверки, контрольные точки и журналирование выполняются только в analysis/vendor-behavioral-reconciliation. Не создавать параллельные ветки разработки и не продолжать работу в удалённых исторических ветках.

Коммиты, создаваемые через GitHub Contents API, сразу записываются в удалённую рабочую ветку. Для составных изменений допускается создание одного Git commit через Git Data API с несколькими изменёнными файлами. Каждая логически завершённая операция должна иметь отдельный осмысленный commit.

На дату сверки GitHub API возвращает только две ветки:

| Ветка | Статус | Действие |

## Default branch

Пользователь разрешил назначить analysis/vendor-behavioral-reconciliation веткой GitHub по умолчанию. После изменения:
1. открыть Settings → General → Default branch;
2. выбрать analysis/vendor-behavioral-reconciliation;
3. подтвердить изменение;
4. проверить, что GitHub открывает README рабочей ветки по корневому URL.

Это изменение не объединяет ветки, не переписывает main и не закрывает PR. До подтверждения настройки GitHub корневой URL может продолжать показывать main.

## Обязательные правила

1. Перед изменением проверить текущий HEAD и прочитать целевой файл.
2. Не использовать массовое добавление/удаление файлов без аудита.
3. Утверждённую E3, её XML-netlist и тег gost-e3-approved-2026-11-01 не изменять при редактуре документации.
4. Статусы APPROVED, VERIFIED, PRELIMINARY, BLOCKED и HISTORICAL применять только в пределах фактически выполненной проверки.
5. Не объявлять производственную готовность по наличию KiCad-файла. Для PCB нужны проверенные footprints, трассировка, ERC/DRC, 3D-проверка и производственные экспорты.
6. Не смешивать SPICE, расчётные допущения и аппаратные измерения.
7. Исторические материалы сохранять для прослеживаемости. Из основного маршрута чтения их исключать через навигацию и статусные предупреждения, а не удалять.
8. После каждого логически завершённого изменения создавать отдельный commit и проверять его присутствие в удалённой ветке.
