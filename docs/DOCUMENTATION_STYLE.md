# Стандарт оформления инженерной документации

**Область действия:** главная страница GitHub, навигационные документы, каталоги иллюстраций и Markdown-материалы проекта.  
**Рабочая ветка:** analysis/vendor-behavioral-reconciliation.  
**Цель:** единый читаемый вид технических материалов без изменения инженерного содержания и статусов подтверждения.

## 1. Визуальная система

- Основной язык — русский. Англоязычные обозначения компонентов, интерфейсов, команд и статусов сохраняются в оригинальном виде.
- Заголовок первого уровня используется один раз на страницу. Далее применяется последовательная иерархия H2/H3.
- Навигационные страницы начинают работу с краткого назначения и статуса документа, затем дают быстрые ссылки и только после этого подробности.
- Таблицы предназначены для сравнения параметров и статусов. Большие описательные абзацы не переносить в ячейки без необходимости.
- Для статусов использовать только утверждённые значения: APPROVED, VERIFIED, PRELIMINARY, IN PROGRESS, BLOCKED, NOT STARTED и HISTORICAL. Смысл статуса всегда раскрывать текстом.
- Бейджи и цветовые метки не заменяют пояснение и не должны создавать впечатление сертификации или физической проверки.
- Не применять декоративные эмодзи в заголовках инженерных разделов.

## 2. Формулы LaTeX в GitHub Markdown

GitHub отображает математические выражения средствами MathJax. Для совместимого отображения на страницах README и Markdown использовать следующие ограничители.

**Встроенная формула** — одинарные знаки доллара:

    Рабочий ток определяется как $I=U/R$.

**Отдельная формула** — двойные знаки доллара на отдельных строках:

    $$
    P_{\mathrm{loss}}=U_{\mathrm{CE}}\cdot I_{\mathrm{C}}
    \tag{4.1}
    $$

Если формула содержит выражение, которое конфликтует с разметкой Markdown, допускается специальная inline-запись GitHub с обратными кавычками внутри ограничителей: знак доллара, обратная кавычка, LaTeX, обратная кавычка, знак доллара.

### 2.1 Обозначения и единицы

- Физические величины записывать математически: $U_{\mathrm{пит}}$, $I_{\mathrm{C}}$, $R_{\theta}$.
- Текстовые индексы оформлять через команду \mathrm{} или \text{}: $U_{\mathrm{CE}}$, $t_{\mathrm{доп}}$.
- Единицы измерения отделять от численного значения математическим пробелом: $5\ \text{В}$, $20\ \text{кОм}$, $0{,}8\ \text{с}$.
- Для умножения использовать \cdot, для дробей — \frac{}{}, для диапазонов — типографское многоточие или словесную конструкцию.
- Не заключать формулу в обычные круглые скобки вместо математических ограничителей.
- Не использовать квадратные скобки как самодельные ограничители формул.
- Не помещать математическое выражение в обычный fenced code block. Обычный блок кода предназначен для программ, netlist и команд, а не для визуального набора формул.

Нумерованные формулы оформлять через \tag{номер} внутри математического блока. Номер должен соответствовать разделу и реестру ссылок. После изменения структуры главы проверить нумерацию и все упоминания формул.

## 3. Иллюстрации и графики

- Использовать относительные ссылки на изображения внутри репозитория.
- Для каждого изображения задавать содержательный alt-текст.
- Подпись размещать отдельной строкой после изображения в формате: «Рисунок 4.1 — Название».
- В тексте должна быть ссылка на каждый значимый рисунок. Само наличие файла в каталоге не делает его частью документа.
- Сохранять исходные SVG и скрипты генерации графиков, если они являются воспроизводимыми исходниками.
- Для графиков обязательны название или подпись, подписи осей, единицы измерения, легенда и описание расчётного сценария.
- Визуализации SPICE помечать как результаты моделирования. Они не являются измерениями физического устройства.
- Рисунки предварительной компоновки обозначать PRELIMINARY. Исторические схемы и модели не использовать для описания утверждённой E3.
- Не растягивать растровые изображения и не обрезать позиционные обозначения, шкалы или размерные надписи.

## 4. Таблицы и ссылки

- Единицы измерения указывать в заголовках столбцов или рядом с величиной.
- Числа в одном столбце выравнивать единообразно. Не смешивать десятичную точку и запятую в пределах одной таблицы.
- Для каждой таблицы указывать номер и название над таблицей.
- Ссылки на главы, таблицы, рисунки, схемы и расчёты оформлять относительными Markdown-ссылками.
- Ссылки на внешние паспорта должны вести на документ точного исполнения компонента или явно пояснять, что источник относится к семейству.

## 5. Достоверность и прослеживаемость

- Не заменять отсутствующие фотографии или CAD-изображения вымышленным изображением готового изделия.
- Не выдавать предварительную архитектуру за утверждённую электрическую схему.
- Не повышать статус PRELIMINARY или BLOCKED только ради визуальной привлекательности README.
- Не менять номиналы, связи, состав BOM или результаты расчётов в ходе редакторской правки.
- При выявлении инженерного противоречия фиксировать его в журнале и отдельном пункте проверки. Не исправлять молча.
- Для каждой значимой правки фиксировать дату, состав файлов, проверку и commit SHA в инженерном журнале.

## 6. Проверка перед публикацией

- [ ] Все математические выражения отображаются в GitHub Preview.
- [ ] Нет формул в круглых или квадратных скобках вместо математических ограничителей.
- [ ] Все изображения открываются по относительным ссылкам.
- [ ] Alt-тексты описывают фактическое содержимое изображения.
- [ ] Рисунки имеют номера, подписи и ссылки из текста.
- [ ] Исторические и предварительные материалы явно помечены.
- [ ] Статусы README совпадают с картой прогресса и инженерным журналом.
- [ ] Изменения не затрагивают утверждённую базовую E3 и её тег.
